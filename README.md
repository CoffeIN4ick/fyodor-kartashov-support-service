\# Сервис заявок в службу поддержки



Учебный веб-сервис для работы с заявками в службу поддержки, разработанный в рамках домашнего задания №1 по дисциплине «Оптимизация клиент-серверных приложений».

\## Бизнес-правила



Поддерживаются статусы:



```text

new

in\_progress

closed

```



Для каждой категории задан норматив времени реакции.



Временем реакции считается интервал между созданием заявки и первым комментарием сотрудника поддержки.



Если первый ответ сотрудника превышает норматив категории, заявка считается заявкой с нарушенным нормативом.



Сводка показывает:



\- общее количество заявок;

\- количество заявок с нарушением норматива;

\- долю нарушений;

\- количество открытых заявок по категориям.

\## Программный интерфейс



| Метод и путь | Параметры | Ответ | Ошибки |

|---|---|---|---|

| `POST /api/login` | JSON: `username`, `password` | Данные пользователя и cookie авторизации | `401` |

| `POST /api/logout` | Нет | Сообщение об успешном выходе | `401` |

| `GET /api/me` | Нет | Данные текущего пользователя | `401` |

| `GET /api/categories` | Нет | Список категорий и нормативов | `401` |

| `GET /api/tickets` | `page`, `size`, `status`, `categoryId` | Страница заявок: `page`, `size`, `total`, `items` | `400`, `401` |

| `GET /api/tickets/{id}` | `id` | Карточка заявки, пользователь, категория, комментарии, время реакции и SLA | `401`, `404` |

| `POST /api/tickets` | JSON: `title`, `description`, `categoryId` | Созданная заявка | `400`, `401`, `404` |

| `POST /api/tickets/{id}/comments` | `id`, JSON: `text` | Созданный комментарий | `400`, `401`, `404` |

| `PUT /api/tickets/{id}/status` | `id`, JSON: `status` | Новый статус заявки и `closedAt` | `400`, `401`, `403`, `404` |

| `GET /api/summary` | Нет | Сводные показатели по заявкам | `401` |

# Нагрузочное тестирование и профилирование — ДЗ №2

Во втором домашнем задании проведено нагрузочное испытание и профилирование сервиса заявок в службу поддержки на рабочем наполнении базы данных.

Использовались:

- **k6 v2.4.0** — генерация нагрузки;
- **PowerShell 7** — запуск сценариев и мониторинга;
- **dotnet-trace 10.0** — профилирование приложения;
- **PostgreSQL 16**;
- **ASP.NET Core / .NET 9**.

Нагрузочный тест находится в каталоге:

```text
load/load.js
```

## Профиль нагрузки

Смешанный профиль отражает типичную работу пользователей и сотрудников службы поддержки.

| Операция | Вес | Обоснование |
|---|---:|---|
| `GET /api/tickets` | 30% | Основной рабочий экран, открывается чаще всего |
| `GET /api/tickets/{id}` | 30% | Карточка открывается перед просмотром и действиями |
| `POST /api/tickets/{id}/comments` | 12% | Переписка по заявке выполняется регулярно |
| `PUT /api/tickets/{id}/status` | 8% | Статус меняется несколько раз за жизненный цикл заявки |
| `POST /api/tickets` | 8% | Новые заявки создаются реже, чем просматриваются существующие |
| `GET /api/categories` | 5% | Категории используются при создании и фильтрации |
| `GET /api/me` | 5% | Данные пользователя используются интерфейсом |
| `GET /api/summary` | 2% | Сводка просматривается значительно реже списка заявок |

Суммарный вес операций составляет **100%**.

Авторизация выполняется один раз до начала нагрузки и не входит в измеряемый поток запросов.

## Критерии успешного прохождения ступени

Для всех испытаний используются одинаковые пороги:

```text
p95 < 500 мс
доля ошибок < 1%
```

Если нарушается хотя бы одно условие, ступень считается не выдержанной.

## Смешанный сценарий

Смешанный профиль запускается в открытой модели нагрузки `constant-arrival-rate`.

Пример запуска:

```powershell
k6 run `
  -e MODE=mixed `
  -e RATE=16 `
  -e DURATION=30s `
  .\load\load.js
```

Параметры:

- `MODE=mixed` — смешанный профиль;
- `RATE` — заданная частота в запросах/с;
- `DURATION` — длительность ступени.

Испытанные ступени:

```text
2 → 4 → 8 → 16 → 32 → 64 → 128 запросов/с
```

### Результаты смешанного профиля

| Заданная частота | p95 | Максимум | Ошибки | dropped_iterations | Фактическая частота |
|---:|---:|---:|---:|---:|---:|
| 2 req/s | 56,42 мс | 1,41 с | 0,00% | 0 | 2,02 req/s |
| 4 req/s | 60,51 мс | 1,32 с | 0,00% | 0 | 3,97 req/s |
| 8 req/s | 29,63 мс | 3,35 с | 0,00% | 0 | 7,97 req/s |
| 16 req/s | 47,54 мс | 3,53 с | 0,00% | 0 | 15,91 req/s |
| 32 req/s | 52,44 мс | 5,20 с | 0,00% | 0 | 31,75 req/s |
| 64 req/s | 69,68 мс | 5,42 с | 0,00% | 0 | 63,52 req/s |
| 128 req/s | 7,16 с | 16,95 с | 2,44% | 564 | 83,78 req/s |

**Допустимая интенсивность смешанного профиля — 64 запроса/с.**

**Первая неуспешная ступень (точка излома) — 128 запросов/с.**

На ступени 128 запросов/с одновременно нарушены оба порога: `p95 = 7,16 с`, доля ошибок `2,44%`, зафиксировано `564 dropped_iterations`.

## Проверка гипотез ДЗ №1

### Гипотеза 1 — подтверждена с уточнением

Предполагалось, что главное узкое место `/api/summary` связано с обработкой большого объёма данных.

Получено:

```text
1 req/s → p95 = 2,22 с
4 req/s → p95 = 10,75 с
```

Профиль показывает значительную долю времени в цепочке EF Core/Npgsql. Проблема связана с загрузкой, материализацией и последующей обработкой большого набора связанных данных.

### Гипотеза 2 — подтверждена

Предполагалось плохое масштабирование сводки с ростом количества заявок и комментариев.

При заданных 8 запросах/с контрольный запуск показал:

```text
p95 ≈ 41,57 с
фактическая частота ≈ 1,73 req/s
dropped_iterations = 55
```

Фактическая пропускная способность перестаёт расти, тогда как задержка увеличивается до десятков секунд.

### Гипотеза 3 — отдельно не проверена

Гипотеза касалась умеренного роста времени:

```text
GET /api/tickets?page=1&size=20
```

Отдельное ступенчатое испытание этой операции не выполнялось. При этом смешанный профиль выдержал **64 запроса/с** при `p95 = 69,68 мс` и `0%` ошибок, поэтому получение списка заявок не является главным ограничивающим местом сервиса.

## Направление оптимизации для ДЗ №3

Основным направлением дальнейшей оптимизации является:

```text
GET /api/summary
```

Необходимо уменьшить объём данных, загружаемых из PostgreSQL, и сократить материализацию большого графа заявок и комментариев.

В ДЗ №3 планируется перенести необходимые агрегаты и расчёты ближе к базе данных вместо загрузки большого набора сущностей и последующей обработки в памяти приложения.

Основания:

```text
p95 при 1 req/s = 2,22 с
максимальная наблюдаемая пропускная способность ≈ 2,7 req/s
p95 при 8 req/s достигает десятков секунд
NpgsqlReadBuffer ≈ 67,08% inclusive
EF Core lambda_method ≈ 62,05% inclusive
```

Оптимизация `/api/summary` в ДЗ №2 не выполнялась, чтобы результаты нагрузочного испытания оставались исходной точкой перед изменениями в ДЗ №3.
